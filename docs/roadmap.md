# Roadmap, build cadence, and open gaps

**This repo is pre-1.0 and openly a work in progress.** No version has been declared working yet. This page is where that's tracked honestly — what's built, what's next, what's known to be incomplete, and what would have to be true to call a version done.

Two other cadences exist and are different from this one: the **Discovery & Advisory Cadence** (how an agent guides a person through decisions) and the **Agent Operating Cadence** (how an agent executes against real infrastructure). Both live in [`methodology.md`](methodology.md). The cadence below is about how *this repository* gets built — a separate concern that happens to share the word.

## Build cadence

Phased, each phase closing with a `CHANGELOG.md` entry and a version tag. The tags are the checkable evidence the cadence is real rather than aspirational.

| Phase | Scope | Status |
|---|---|---|
| **0 — Repo hygiene** | `LICENSE`, `.gitignore`, `CONTRIBUTING.md`, root `AGENTS.md` / `CLAUDE.md`, `docs/methodology.md` | Built → `v0.3.0` |
| **1 — Discovery layer** | `discovery/` — needs, hardware envelope, AI tooling, each criteria-based rather than brand-based | Built → `v0.3.0` |
| **2 — Foundation blocks** | `blocks/foundation/host-platform/` (isolation/storage/simplicity/raw-control axes) and `blocks/foundation/network/` (topology, addressing) — both consuming discovery's output | Built → `v0.3.0` |
| **3 — Flagship domain block** | `blocks/domains/proxmox-ai-stack/` — Proxmox + GPU passthrough + AI services, requiring all four foundation blocks | Built, **`L0`** → `v0.3.0` |
| **4 — Validation** | Climb the [verification ladder](methodology.md): desk-check against current vendor docs, retro-validate against a real running deployment, execute what nested virtualization can reach, then real hardware. Fix what breaks | **Started 2026-08-12 — the ladder and its CI check exist; every block is still `L0`** |
| **5 — Block schema for future categories** | `docs/block-schema.md` formalizing CEP + `requires:` + manifest fields, so media / home-automation / personal-cloud blocks can be added without inventing structure | Built → `v0.3.0` |
| **6 — Composition examples** | `examples/` showing multiple blocks combined, demonstrating how `requires:` and the manifest compose | Not started |
| **7 — Community layer** | `.github/ISSUE_TEMPLATE`, `.github/PULL_REQUEST_TEMPLATE.md` with the validation attestation | Built → `v0.3.0` |

Phases 5 and 7 landed early alongside the blocks they describe rather than strictly in order. That's fine — the ordering is a dependency guide, not a schedule.

**Phase 4 was re-scoped on 2026-08-12, and the reason is worth recording.** It used to read "run discovery → host-platform → flagship end to end against real Proxmox hardware," which describes a test only a cold-start user who owns nothing can run — while also requiring hardware. That bundled two different questions with different costs and different test subjects: whether the *content* is correct (needs real infrastructure), and whether the *guidance* routes a real person well (needs a cold reader, and is free). Bundled, the phase was blocked on hardware nobody was going to buy for the purpose. Split, most of it was already startable — and one part of it, the cold walkthrough, had in fact already been done twice and produced this list's most useful entries. A phase whose completion requires a person who doesn't exist hides the small unblocked work inside it, which is why the ladder replaced it.

**A third thing landed after `v0.3.0`:** **`blocks/foundation/agent-operations/`**, which owns everything after the build — the structural contract that keeps `.homelab-state.yml` from decaying into a session journal, where findings go the moment they're found, what counts as proof a change landed, and a maintenance pass that checks drift in both directions. The repo previously ended at "flagship deployed" and had no home for day-2 at all. Its content comes from a real deployment operated by AI agents for months; see [`field-evidence.md`](field-evidence.md), including why that provenance doesn't move it off `L0`.

**Two other things landed after `v0.3.0` that were not in the original phase list**, both because closing gap G3 turned out to require them. **`start-here/`** — the phases above built the content an agent works *through* and never built the thing that tells an agent how to move between them. **`blocks/foundation/hardware-bringup/`** — the cold walkthrough found that nothing owned the stretch between deciding a platform and having a machine to run it on. Both slot before Phase 4 in dependency order (a dogfood session has to start somewhere, and on something), and neither is its own phase, since both are infrastructure for the existing ones rather than new scope.

**Why one tag and not three.** This table originally promised a tag per phase — `v0.1.0` at discovery, `v0.2.0` at the foundation blocks, `v0.3.0` at the flagship. The git history can't carry that: phases 0–3, 5, and 7 landed inside two commits on a single branch, so no commit boundary matches a phase boundary. Placing three tags would mean picking arbitrary commits and calling them releases, which is exactly the kind of claim-without-evidence this page exists to avoid. They close together under `v0.3.0` instead. Future phases get their own tags, since they'll land as their own work.

**Deliberately not built yet:** media, home automation, and personal-cloud/backup domain blocks, and everything in the `core-services` tier (reverse proxy, DNS, auth/SSO — see `docs/block-schema.md`). `blocks/foundation/host-platform/` was broadened (2026-08-06) to name four decision axes — isolation, storage, simplicity, raw-control — but that's decision-layer text, not new infrastructure; it doesn't create new folders. Candidate future *domain* blocks that would build on the storage and simplicity axes specifically: a TrueNAS SCALE storage/media block, an OpenMediaVault lightweight-NAS block, a CasaOS simple-dashboard block. Candidate future *core-services* blocks: `reverse-proxy`, `dns`, `auth-sso` — every domain block added after the flagship will want at least the first two, so these move up in priority once a second domain block is proposed. Named here so the intent is tracked; folders stay uncreated until someone actually writes one. A directory of empty stubs would make the repo look broader than it is, which is the opposite of useful.

## Versioning

Pre-1.0, `0.x.y`, and the `0.` is meaningful rather than modest:

- **`0.x`** — the structure is real and usable, but no block has been validated end-to-end against real hardware. Interfaces (the CEP shape, `requires:`, the manifest schema) may still change.
- **`1.0`** would mean: at least one complete path — discovery → all four foundation blocks → a domain block — reaches **`L3` with `unreached: none`**, or `L4`. That's the precise form of "dogfooded against real hardware": executed start to finish with nothing the environment couldn't test. It also requires the task-completion test below to pass, and every block to state its rung prominently.

**Nested virtualization does not buy `1.0`, deliberately.** It can carry blocks a long way up the ladder — a real Proxmox install, real VM creation, real container work — and that's worth having. But `unreached` on such a run will list GPU passthrough, IOMMU grouping, firmware settings, and physical disks, and a `1.0` that shipped with those untested would be claiming a test that never happened.

Until then, treat everything here as a well-structured draft that hasn't met reality yet.

## The three metrics

Only three, tracked deliberately. Stars and forks are excluded — they measure attention, not whether the thing works.

**1. CEP completeness** — how many blocks have a complete Checklist + Example + Placeholders triple.

| Block | Checklist | Example | Placeholders | Complete |
|---|---|---|---|---|
| `discovery/needs.md` | yes | yes | yes (n/a, stated) | yes |
| `discovery/ai-tooling.md` | yes | yes | yes (n/a, stated) | yes |
| `discovery/hardware-envelope.md` | yes | yes | yes (n/a, stated) | yes |
| `blocks/foundation/agent-operations/` | yes | yes | yes | yes |
| `blocks/foundation/host-platform/` | yes | yes | yes | yes |
| `blocks/foundation/hardware-bringup/` | yes | yes | yes | yes |
| `blocks/foundation/network/` | yes | yes | yes | yes |
| `blocks/domains/proxmox-ai-stack/` | yes | yes | yes | yes |

**8 / 8 structurally complete**, and this row is now checked by CI rather than by counting — `.github/workflows/validate-blocks.yml` fails the build on a missing CEP file, so the number can't quietly go stale. Note what this metric does and doesn't say: it counts whether the three parts exist and are genuinely filled, not whether their contents are correct. Metric 3 is what tests correctness.

`start-here/` is deliberately not a row and never will be. It isn't a block — there's nothing in it to adapt, so a CEP triple would be three empty ceremonies. Same reason `discovery/README.md` isn't a row while the three discovery topics are. The denominator counts blocks and discovery topics; adding non-block folders to it would inflate the number without measuring anything.

**2. Verification floor** — the lowest rung any block sits on, plus the oldest `last-verified` date once dates exist.

Currently **L0 — floor and ceiling both.** All five blocks sit at `L0`: written from official documentation, never checked against anything.

This replaced "oldest `last-verified` date," which could only ever read `n/a` until the first block was fully dogfooded, and so measured nothing for as long as it mattered most. A floor moves the first time any block gets desk-checked, which makes progress visible while it's still cheap — and because the floor is the *lowest* rung, it can't be gamed by promoting the one block that was easiest to validate. CI enforces that a claimed rung carries its evidence artifact, so this number can't drift ahead of reality.

**3. Task-completion test** — can an agent, given *only* one block plus the manifest schema, complete a named realistic task without asking for out-of-band context? Run manually each release as a pass/fail gate.

Named task for the flagship: *"Create a GPU-passthrough VM on the existing Proxmox node and deploy a local LLM with a chat interface, touching nothing else."* Currently **untested against real hardware.** A static review in August 2026 found four missing facts that would have blocked an agent (host access method, single-GPU console lockout, q35/OVMF requirement, in-VM GPU driver and container runtime); those have been added to the checklist, but static review is not the test.

**This metric is the guidance-quality axis, and it needs a cold reader rather than cold hardware** — which makes it the cheapest evidence in the repo and the reason it isn't blocked on anything. The rungs measure whether a block's *content* is correct; this measures whether an agent following the repo actually routes a real person well. Its evidence artifact is a **transcript**: hand `start-here/TRAVERSAL.md` to a fresh session with a novice persona and record where it gets lost. Two such walkthroughs have been run (2026-08-06, and the one that produced `hardware-bringup/`), and between them they account for most of the entries on this page — including the two structural gaps nobody had noticed from the inside. `discovery/` and `start-here/` carry no rung precisely because this is how they get tested.

## Open gaps

The running list. Items get struck through and dated when closed, not deleted.

**Gap ids are stable and never reused.** They're written as literal `G` labels rather than as an ordered list, because a Markdown ordered list renumbers itself from its first item — so closing one gap silently shifted every later number and left cross-references pointing at the wrong thing. That happened here on 2026-08-12, when closing the `assumes:` gap turned `G8` and `G9` into a rendered 7 and 8. A retired id (currently `G7`) just stays absent; a hole in the sequence is information, not an error. Changelog entries from before 2026-08-12 use the old positional numbering and don't map onto these ids.

**Blocking 1.0:**

*These three, and only these three, are mirrored as GitHub issues under the [`1.0` milestone](https://github.com/davigms-pve/Homelab_AIStack/milestone/1) — `G1` is [#4](https://github.com/davigms-pve/Homelab_AIStack/issues/4), `G2` is [#5](https://github.com/davigms-pve/Homelab_AIStack/issues/5), `G3` is [#6](https://github.com/davigms-pve/Homelab_AIStack/issues/6). The issues are a visibility surface for people who never open this file; the gaps here stay the record, and the issue bodies deliberately hold no content of their own. Close the issue when you strike the gap. Everything below the 1.0 section is tracked here only.*

- **G1 — Get `blocks/domains/proxmox-ai-stack/` to `L3` with `unreached: none`.** This is the single biggest gap and the reason the flagship reads `L0`. Closing it means a live agent session creating a real VM with real GPU passthrough on real hardware, following only what's in the block; every command confirmed or corrected; the frontmatter and both READMEs updated to match. Needs hardware and an operator — that residue has no synthetic substitute, and it's the accepted cost of the bring-your-own-infra path.

   **But most of this block can climb without any of that**, which is the point of splitting the rungs — see gaps G10 and G11 for the two unblocked steps.

   *Named suspects to check first, so `L0` reads as a prediction rather than a disclaimer:* the example sets the IOMMU kernel argument via `/etc/kernel/cmdline` + `proxmox-boot-tool refresh`, which is the systemd-boot path used on ZFS-root installs — a GRUB-booted node needs `/etc/default/grub` + `update-grub` instead, and the example currently doesn't branch on that. Also unconfirmed: whether the vendor driver install inside the VM needs the host to hide the hypervisor from the guest, and whether the stated `q35` + OVMF combination is sufficient on consumer motherboards with less clean IOMMU grouping than the example assumes.
- **G2 — Walk the foundation blocks — `agent-operations/`, `host-platform/`, `hardware-bringup/`, and `network/` — with a real person.** `agent-operations/` is the newest and the one whose failure mode is slowest to show: its contract either holds over months of real sessions or it doesn't, and a single walkthrough can't tell you which. What a walkthrough *can* catch is whether its two questions land, and whether the finding-routing rule survives contact with someone who has no issue tracker. `host-platform/` and `network/` are decision layers and lower risk than the flagship, but all four are equally at `L0` and shouldn't quietly ride along on the flagship's validation. **`hardware-bringup/` is the one to walk first and the hardest to fake**: its checkpoints have never met a real parts order, a real assembly, or a real first connection, and unlike the other two its failure modes cost money rather than time. Its protocol was designed from a walkthrough that *found* the gap, not from a completed build. `network/` in particular is untested against a real VLAN-capable switch/router — the worked example assumes 802.1Q trunking support that's never been confirmed against real consumer hardware.
- **G3 — Cold-walkthrough `discovery/`.** **Run once, 2026-08-06 — findings recorded below, gap stays open.** The run produced real defects rather than a clean pass, which is the useful outcome, but it did *not* produce a self-consistent decision set end to end: it stopped before the envelope was final, and G4 and G5 below mean the journey structurally cannot complete yet. Re-run after those close. The persona used: an enthusiast with a laptop and an underpowered Pi, $2–3k, storage-first, wanting personal cloud → media → AI in that order.

**From the 2026-08-06 cold walkthrough:**

- **G4 — Three of the four discovery categories still have no block.** `discovery/needs.md` offers AI, media, home automation, and personal cloud; only AI has a block. In the 2026-08-06 walkthrough the person's top *two* priorities were uncovered, so discovery produced a decision set the repo could not act on. **Half-closed 2026-08-06:** `start-here/TRAVERSAL.md` now has defined behavior when `priority` names a category with no block — say so plainly, offer the covered ones, point at the block-gap template, and never silently promote their second choice. That stops the agent improvising, but it doesn't build anything. **Still open:** `personal-cloud`, `media`, and `home-automation` domain blocks. Sequencing note: G9 below now gates these — four domain blocks without a shared reverse proxy and DNS will each reinvent them and drift apart immediately.
- **G5 — Minor — the methodology agreement is presented before comfort level is known.** `TRAVERSAL.md` puts it "before anything else"; the Discovery & Advisory Cadence says calibrate to comfort level immediately, and `needs.md` calls that "the very first question." So the one message guaranteed to be mis-pitched is the first one. Low cost, real ordering conflict.

**Known content gaps:**

- **G6 — No `examples/` directory (Phase 6).** Nothing yet demonstrates two blocks composing, which is the main thing `requires:` exists for. This gets more valuable once a second domain block exists.
- **G8 — Cost questions have no home in discovery.** The walkthrough persona ranked local AI third *conditionally* — "I want to know how much it costs me" — so their priority order literally depended on an answer the repo has no defined way to give. `budget_band` captures a number; nothing captures "is this worth it." The repo is right not to track prices, and answering in cost *shape* (one-time hardware vs. ongoing power vs. subscription avoided, plus the honest quality tradeoff of a local model) stays inside the criteria-not-picks rule — but the agent had to invent that move. `discovery/needs.md` asks for a priority ranking without acknowledging that a ranking can be conditional.
- **G9 — `core-services` tier is named but empty — and G4 makes this urgent.** Every domain block after the flagship will want a reverse proxy and DNS at minimum. That was deferrable while one domain block existed; committing to three more (`personal-cloud`, `media`, `home-automation`) means `reverse-proxy` and `dns` now come first or alongside them, or each of the four reinvents its own reverse-proxy instructions and they drift apart immediately.

**Unblocked rungs — added 2026-08-12, none of these need hardware:**

- **G10 — Desk-check every block to `L1`.** Read each command, flag, and prerequisite against the vendor's current official documentation and record the date and versions. Costs an afternoon per block and needs nothing but a browser. It's the fastest way to move the verification floor off `L0`, and it's the rung most likely to catch the specific suspects already named under G1 — the `/etc/kernel/cmdline` vs GRUB branch is answerable from Proxmox's own docs without booting anything.
- **G11 — Retro-validate the flagship and `host-platform/` to `L2` against the private deployment.** Walk each checklist item backwards against a real running server and record every place they disagree. Two rules make this honest rather than circular: the deployment partly informed these blocks, so **agreement proves little and divergence is the whole product**; and each divergence forces a recorded decision — is the block wrong, or is that deployment idiosyncratic? The divergence log is the evidence artifact, and it's useful template content in its own right ("where real deployments legitimately deviate"). A zero-divergence result means the walk wasn't done item by item.
- **G12 — Execute a nested-virtualization pass.** Proxmox installs fine inside a VM, so the install path, `qm`/`pvesh` command syntax, q35 + OVMF selection, bridge and VLAN-aware configuration on the host side, and the whole in-guest Docker and CPU-only inference layer can all be genuinely run. Reaches `L3` with a non-empty `unreached:` list — GPU passthrough, IOMMU grouping, firmware settings, physical disks, and real switch trunking stay out of reach. **One trap to write into the run record:** a nested install validates whichever bootloader it happened to use, so it can "confirm" one branch of the `/etc/kernel/cmdline`-vs-GRUB fork while leaving the other untested and looking like coverage. Test both deliberately or record which one you got.

**Known content gaps (continued):**

- **G13 — Three operational gotchas have no owning block.** NFS `soft` vs `hard` mounting (a `hard` mount can freeze a host in uninterruptible sleep when the server side dies), cron drop-ins not inheriting an interactive shell's `PATH`, and syntax-checking code before restarting a service on it. All three cost real debugging sessions in the deployment behind [`field-evidence.md`](field-evidence.md), and all three were deliberately **not** forced into an existing block — this repo has no storage block, no scheduled-job content, and no service-management content, and guidance placed where no block owns the topic is scope creep. They appear only as illustrative content inside `agent-operations/AGENTS.md.example`. A future storage or core-services block should adopt the first; the other two want a day-2 execution block that doesn't exist yet.
- **G14 — `agent-operations/` preaches mechanical enforcement and ships prose.** Its central rule is that a written convention is advice and only a mechanism is a rule — and this repo took its own advice with `.github/workflows/validate-blocks.yml`. But the contract that block hands to a *user's* repo (`next:` capped at three, every open item carrying a reference, `handoff:` drained first) is enforced by nothing except the next session's willingness to follow it. The honest version would ship a small validator the user's own repo can run against `.homelab-state.yml`. Naming this rather than pretending the prose is enough.
