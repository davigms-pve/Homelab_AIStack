## [Unreleased]

### Added (verification map, 2026-10-08)

- **[`docs/verification-map.md`](docs/verification-map.md)** — for every artifact the repo ships, which rungs of the ladder can ever apply, and for the command-bearing and decision blocks, which individual checklist items each evidence environment (desk, the private deployment, nested virtualization, real hardware) can and can't reach. It exists because the rungs reach *different subsets* of a block and so don't stack: a nested-virtualization run covers the install path and misses the whole passthrough section; the private deployment covers passthrough and misses everything about bring-up; and some items came *from* that deployment, so its agreement with them is circular. Writing that down turns "get the flagship to `L3`" from one task into four with known blind spots, and gives a nested run a predicted `unreached:` list before anyone starts. **It is a prediction, not evidence** — nothing in it moves a rung — and its Private column was written without access to the deployment, so the maintainer's corrections are the first thing it needs.
- Four-way sort of what the ladder fits: the flagship (full ladder); `host-platform`, `network`, `hardware-bringup` (partial); `agent-operations` (poor fit); `discovery/` and `start-here/` (off the ladder, on the guidance-quality axis `methodology.md` already assigns them).
- Three gaps the sort exposed. Two were decided the same day, with the maintainer, and now live in `methodology.md`: **`agent-operations` moves to the guidance-quality axis** (G15 — no vendor to desk-check against, real test is months of adoption), and **`1.0` becomes two gates** (G16 — a content gate for the executed path, `L3` with `unreached: none` or `L4`, and a guidance gate: a real person walked through discovery and the decision blocks, transcript as evidence; before this, `1.0` required an `L3`/`L4` path through things that cannot hold a rung). **G17** stays open: nothing checks the map's status table against the frontmatter.

### Changed (2026-10-08)

- **`1.0` is now two gates, not one rung requirement.** Content gate: the executed path reaches `L3` with `unreached: none`, or `L4` (unchanged in substance; nested virtualization still doesn't count). Guidance gate, new: a real person who didn't write the content is walked through `discovery/`, `start-here/`, `host-platform/`, `network/`, `hardware-bringup/` and one session of `agent-operations/`, with a transcript as evidence. The old single requirement was unmeasurable for three members of its own path. `docs/methodology.md` owns the definitions; `docs/roadmap.md`'s versioning section points at them.
- **`agent-operations/` is moved onto the guidance-quality axis** rather than stretched across the ladder. It keeps `L0` in its frontmatter (CI requires a rung), and its README says where its real evidence lives. Adoption by a real repo is its long-run evidence and is not required for `1.0`.

### Fixed (2026-10-08)

- `hardware-bringup`, `host-platform`, and `network` `AGENTS.md.example` files still opened with `**Status: unverified.**` — the pre-ladder vocabulary — while their frontmatter said `L0`. They now lead with the rung. "Every block states its rung prominently" is a `1.0` requirement, and an old label sitting beside a new one is the quiet kind of drift this repo is meant not to have.

### Added (agent governance baseline, 2026-09-02)

PR #7. `AGENTS.md` is the file an agent actually reads in this repo, and it said nothing about branching, pushing, or merging. That is worse than having no file, because a file that is being read but omits the one thing that matters reads as though the repo were already governed. Several agent toolchains document a workflow whose normal last step is squash-merging their own PR, and with nothing written here to oppose it, that default stood — in a **public** repo, where a bad merge is visible and forkable before anyone can revert it.

- **`AGENTS.md`, "Working alongside other agents (and the humans reviewing them)".** Never push to `main` and never merge your own work — open a PR and stop, no matter how small the change; the maintainer merges. An explicit statement that a toolchain's own merge-by-default workflow does not apply here. One branch per contributor and a separate branch per agent (`<handle>/<topic>` for human-only work, `<agent>/<handle>/<topic>` for agent work; branches that predate the convention stay valid). No edits to `.github/workflows/` — an agent that can weaken the backstop and then rely on it in the same run has no backstop. No force-push, no `rm -rf` outside the agent's own working tree, no granting credentials or access. Report honestly: if CI fails, say so and quote it; if something was skipped, say which part. The file also states plainly that **none of this is enforced by GitHub** — there is no branch protection, and the rules hold only because an agent reads and follows them. That is a deliberate choice of governance by instruction rather than by narrowed credentials, and it means an agent's honesty is load-bearing here.
- **`.github/workflows/secret-scan.yml`** and **`.github/scripts/secret-scan.sh`**, runnable locally with `bash .github/scripts/secret-scan.sh`. `CONTRIBUTING.md`'s Definition of Done has always banned real IPs, hostnames, tokens and serial numbers in filled examples, but the only check was a contributor ticking a box — in a public repo that deliberately ships realistic-looking values, which is exactly the condition under which a real value slips in unnoticed, because it looks like every value around it. The scan checks the two things a machine can decide without judgment: credential shapes, and IPv4 literals outside the RFC 5737 documentation ranges and RFC 1918 private ranges. The repo already used `192.0.2.x` and `198.51.100.x`, so this locks in existing practice rather than imposing a new one. Hostnames and serial numbers deliberately stay with human review — no script can tell `pve1` from a real node name.
- **`.github/workflows/issue-close-guard.yml`.** Reopens any issue that GitHub closed from a commit-message keyword. An inbound issue is someone taking the trouble to report what broke, and `CONTRIBUTING.md` names the failure mode as one arriving and leaving no roadmap entry behind — a keyword close is exactly that, silently. GitHub parses neither negation nor quotation, so even a commit that says "does not fix #N" closes #N; a guard makes it structurally impossible where a convention could not. Closes through the UI or API carry no commit id and are never touched, so deliberate closes are unaffected.

No block content, schema, or validator behaviour changed.

### Added (field-lessons remediation, 2026-08-12)

Source: an assessment of this repo against a real, private, single-server deployment — Proxmox, dual GPUs, local inference, operated day to day *by AI agents* for months. That deployment transfers *operating* experience, not bring-up experience, and [`docs/field-evidence.md`](docs/field-evidence.md) is the ledger recording what came from it, where each lesson was routed, and why none of it counts as verification.

- **`blocks/foundation/agent-operations/`** — the block that owns everything after the build. The repo previously took someone from "own nothing" to "flagship deployed" and then stopped: `docs/manifest-schema.md` said how the two tracking files get *written* and nothing said how they stay true a year later. This block owns the structural contract that keeps `.homelab-state.yml` a pointer rather than a session journal (no narrative, every open item carrying a reference, `next:` capped at three, a bounded `handoff:` the next session drains first), where a finding goes *at the moment it's found* in a form that works with no issue tracker, what counts as proof a change landed, secrets keyed to the direction a file travels, and a maintenance pass that checks drift in **both** directions — bloat is easy to see, context that's too thin shows up as a session re-making a recorded mistake. It runs first in the foundation tier, because its contract governs files that get their first lines written during discovery.
- **The verification ladder** — `L0` researched → `L1` desk-checked → `L2` retro-validated against a running deployment → `L3` executed → `L4` reproduced by someone else, replacing the three-outcome model in `docs/methodology.md`. Same axis as before (has anyone checked this against reality, never who wrote it), higher resolution: a single `unverified` flag said the same thing about content nobody had read against a vendor doc and content walked line by line against a real server. **Every rung above `L0` names an evidence artifact, and a rung without its artifact isn't a rung.** Two definitions carry the honesty: `L2` requires a *divergence log*, because a block checked against the deployment that informed it can agree with itself for free — divergence is the product, and a zero-divergence result reads as suspect. `L3` requires an `unreached:` list, so an execution run in an environment that structurally can't test GPU passthrough says so; **`unreached: none` is the bare-metal condition, and it's what `1.0` requires.** All five blocks currently sit at `L0`.
- **CI — `.github/workflows/validate-blocks.yml`** and the plain-bash validator behind it, runnable locally with `bash .github/scripts/validate-blocks.sh`. It enforces what a machine can: complete CEP triples, well-formed verification frontmatter whose fields agree with the claimed rung, evidence paths that actually exist, no `<<TOKEN>>` surviving in a filled example, `requires:` names that resolve, block names unique across tiers. This is the field lesson that cost the deployment the most — the same mistake repeated four times, twice *after* the rule was prominently written down, ended not by better wording but by a guard that made it structurally impossible. Every check here used to be a bullet a contributor attested to by ticking a box.
- **`.github/ISSUE_TEMPLATE/dogfood-report.md`** — the `L4` intake. For a public template repo an external reproduction is worth more than any amount of self-checking, because the author is the least-cold reader of this content on Earth.
- **`docs/field-evidence.md`** — deliberately a short ledger rather than the 220-line essay the source material would have supported. A doc nobody opens at the moment a rule applies is the same rule lost, which is one of the lessons it records.

### Changed (2026-08-12)

- **Phase 4 was re-scoped from "Dogfood" to "Validation."** It used to describe a test only a cold-start user who owns nothing could run, while also requiring hardware — bundling content correctness (needs infrastructure) with guidance quality (needs a cold reader, and is free). Bundled it was blocked; split, most of it was already startable, and the cold-walkthrough half had in fact already been run twice and produced most of the roadmap's useful entries. Three unblocked rungs are now tracked as gaps G10–G12, including a nested-virtualization pass. **Nested virtualization deliberately does not buy `1.0`** — it can carry blocks a long way up, but its `unreached:` list will always name the things `1.0` is about.
- **Metric 2 changed from "oldest `last-verified` date" to "verification floor."** The old metric could only read `n/a` until the first block was fully dogfooded, so it measured nothing for exactly as long as it mattered most. A floor moves the first time any block gets desk-checked, and being the *lowest* rung it can't be gamed by promoting whichever block was easiest.
- **Metric 3 named as the guidance-quality axis**, with a transcript as its evidence artifact. `discovery/` and `start-here/` carry no rung, because this is how they get tested.
- `docs/methodology.md`'s Agent Operating Cadence gained a **stop rule** ("an error, an unexpected result, or a disproven premise mid-plan is a decision fork to surface, not something to route around — stop and re-plan is a successful outcome"), a **live-artifact standard** replacing the old "verify" step, and an explicit **owner-only boundary**: obtaining credentials and interactive authentication flows are drafted and handed over, never performed, however much autonomy was granted.
- `docs/manifest-schema.md` gained the state-file structural contract, `next:`/`handoff:` sections, decision-records-before-execution and never-silently-edited rules for `HOMELAB.md`, stable finding ids, and redaction keyed to direction of travel — the rule that live→repo mirrors get redacted and repo→live deploys never do, because a placeholder would ship.
- Domain blocks now require all four foundation blocks; `agent-operations` is first in the traversal order.
- **A `1.0` milestone exists on GitHub**, with the three 1.0-blocking gaps (`G1`–`G3`) mirrored as issues under it. No due date, deliberately: 1.0 is gated on hardware that may never be bought and on a stranger's dogfood report, and a date would be a claim this repo can't back. The mirror is scoped to those three and no further — `docs/roadmap.md` stays the record, issue bodies are pointers holding no content of their own, and everything outside the 1.0 section is tracked in the roadmap only. Two surfaces describing the same work is a drift risk accepted knowingly in exchange for visitor orientation, and bounded to three items so the sync cost is three closures, ever.
- **Roadmap gaps now carry stable `G` ids instead of ordered-list numbers.** A Markdown ordered list renumbers from its first item, so closing the `assumes:` gap silently shifted two later gaps' rendered numbers and left an internal cross-reference pointing at the wrong item — found the same day it was introduced. Ids are now literal and never reused; the absent `G7` is a closed gap, not a mistake. Entries in this changelog dated before 2026-08-12 use the old positional numbering and do not map onto the new ids.

### Fixed (2026-08-12)

- `assumes:` had no Definition-of-Done entry — a block could ship with human prerequisites undeclared, or with an assumption declared and no fallback, which is the failure that field exists to prevent. It's now its own DoD line and its own PR-template checkbox. The `requires:`-resolves half is enforced by CI; whether a fallback is *real* stays a human check, because no script can judge that.

### Added (cold-walkthrough remediation, 2026-08-07)
- **`blocks/foundation/hardware-bringup/`** — the block nothing owned: buying parts, assembling, installing the platform, getting it on the network, enabling remote access. Deliberately thin. It owns the *protocol* — three checkpoints (before money moves, after assembly, first connection), the verification questions at each, the resume contract, universal safety notes, and a standing rule to point at the manuals rather than invent a spec — and never the content, because assembly instructions rot, differ per component, and duplicate the box manual. The block says so itself, so nobody later mistakes thinness for incompleteness. Skippable via `excluded` for anyone who already owns a running server.
- **`assumes:`** — a field beside `requires:` declaring what the *human* must be able to do (`physical-assembly`, `os-install`, `bios-firmware`, `network-hardware`). **Every tag ships with a fallback**; a bare assumption is a bug. Announced at block entry with the fallback attached, never discovered mid-block — it exists to prepare someone, never to disqualify them.
- **`awaiting-human` status plus an `awaiting:` record.** `in-progress` on a block stalled three weeks tells the next session work is underway, which is the opposite of true. `agent-resumes-by` is what a fresh session reads to know its first action without re-interviewing anyone.
- **Closed vocabularies** for `comfort_level` (four values), `wants`, and `priority`, with every consumer updated to name real values. `budget_band` and `constraints` stay deliberately open, with the reason recorded, since nothing branches on them.

### Fixed (2026-08-08)
- `docs/methodology.md` stated a validation rule the repo doesn't follow — that first-party blocks are exercised in a live agent session before merge, "that session *is* the test." Four first-party blocks have merged without it. `CONTRIBUTING.md` was the accurate one all along, offering an explicitly-unverified third path. A rule the project openly doesn't follow makes the neighbouring rules look optional, and the neighbours here are the stop-and-confirm gate and the no-unverified-claims norm.

### Fixed (cold-walkthrough remediation, 2026-08-07)

### Added
- `start-here/` — the entry point an agent is handed first. `TRAVERSAL.md` specifies how to read `.homelab-state.yml`, resolve `requires:`, pick the next block, and hand off to the right cadence; `README.md` is the human counterpart. It sits outside the tier system alongside `discovery/` and carries no CEP triple, because there's nothing in it to adapt. Deliberately not named `AGENTS.md.example` — that suffix means "filled template, find-and-replace it," and this file is followed verbatim.
- `discovery/hardware-envelope.md` gained a **Consistency checks** section — six named conflicts an envelope can contain while every individual line looks fine (`ai-stack` wanted with no VRAM figure, fanless alongside a discrete GPU, low idle power alongside a discrete GPU, a VRAM target the budget can't reach, media with fixed storage, and a beginner comfort level facing GPU passthrough). ### Fixed
- **`requires:` was declared everywhere but resolvable nowhere.** It appeared in four shapes — tiered path, bare folder name, discovery-topic name, and a prose `none — this is the starting point.` — of which `docs/block-schema.md` documented two. No file stated how a tiered path maps to a flat `blocks:` status key (last path segment), and `requires: [needs]` resolved to nothing at all, because `docs/manifest-schema.md` deliberately gives individual discovery topics no status entry. Both resolution paths are now specified in `start-here/TRAVERSAL.md`, discovery topics resolve by the `decisions:` keys they produce, and `discovery/needs.md` is normalized to `requires: none`.
- **The worked example didn't survive its own pipeline.** `discovery/hardware-envelope.md` left the GPU fork open ("PCIe x16 slot **or** built-in GPU… flag as follow-up") and preferred sub-15W idle, while `docs/manifest-schema.md` showed `gpu: discrete-required`, `vram_gb: 12`, and `idle_power_w: 35` for the same fictional persona. Running discovery exactly as written could not produce the manifest example. The envelope example now resolves both conflicts in front of the reader — showing the agent walking the person through each tradeoff — and lands on the manifest's values, restoring the continuity the blocks claim.
- The same example's internal contradiction (a PCIe x16 slot alongside a sub-15W idle target and a fanless preference) is resolved, and that class of error is now caught by the named consistency checks rather than left to reviewer attention. Closes roadmap gap #4.
- **`discovery/ai-tooling.md` was the one discovery topic that resolved to nothing.** It stated the chosen tooling class "doesn't need to be written into `.homelab-state.yml`," which left `blocks: discovery` able to flip to `done` without the topic having been worked through at all, and left an advisory-only setup with no recorded reason for stopping at the end of discovery. It now writes `decisions.agent_capability` (`shell-capable` / `advisory-only`), documented in `docs/manifest-schema.md` and read by `start-here/TRAVERSAL.md` to decide whether execution can proceed. An agent knows its own capability class, but recording it is what lets a later session understand why work stopped.

## [0.3.0] — 2026-08-06

First tagged release. Phases 0–3, 5, and 7 of the build cadence landed together on one branch rather than at separate commits, so they close under a single tag — see the phase table in [`docs/roadmap.md`](docs/roadmap.md). This is a `0.x` release in the sense the versioning policy defines: the structure is real and usable, but all three blocks ship `unverified` and the open gaps are tracked in the roadmap.
